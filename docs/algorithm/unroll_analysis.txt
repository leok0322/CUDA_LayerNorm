================================================================================
          #pragma unroll 对 LayerNorm kernel 无实际性能提升的分析
          涉及 kernel：kernel 3（K2 展开版）、kernel 5（K4 展开版）
================================================================================

--------------------------------------------------------------------------------
一、kernel 编号说明
--------------------------------------------------------------------------------

  Kernel 2 = LayerNorm_kernel_double_warp_reduction         （两遍，无展开）
  Kernel 3 = LayerNorm_kernel_double_warp_reduction_unroll  （两遍，有展开）
  Kernel 4 = LayerNorm_kernel_welford_double_warp_reduction （Welford，无展开）
  Kernel 5 = LayerNorm_kernel_welford_double_warp_reduction_unroll（Welford，有展开）

--------------------------------------------------------------------------------
三、原因分析
--------------------------------------------------------------------------------

3.1 原因一（更直接）：每线程循环迭代次数 ≤ 1，根本没有内容可展开
────────────────────────────────────────────────────────────────────

内层循环结构：
  for (col = threadIDX; col < totalCol / 4; col += threadNum)

  threadNum = BLOCK_SIZE = 1024

  各列数对应的每线程迭代次数：
  ┌──────────┬──────────────┬──────────────────────────────────────────────┐
  │ C（列数）│ totalCol / 4 │ 每线程迭代次数                               │
  ├──────────┼──────────────┼──────────────────────────────────────────────┤
  │   128    │      32      │ 32 个线程各 1 次，其余 992 个线程 0 次       │
  │   256    │      64      │ 64 个线程各 1 次，其余 960 个线程 0 次       │
  │   512    │     128      │ 128 个线程各 1 次，其余 896 个线程 0 次      │
  │  1024    │     256      │ 256 个线程各 1 次，其余 768 个线程 0 次      │
  │  2048    │     512      │ 512 个线程各 1 次，其余 512 个线程 0 次      │
  │  4096    │    1024      │ 所有 1024 个线程恰好各 1 次                  │
  └──────────┴──────────────┴──────────────────────────────────────────────┘

  测试范围内 C 最大为 4096，此时每个线程恰好只执行 1 次循环体。
  对只有 1 次迭代的循环执行 #pragma unroll 等同于什么都没做——
  展开的本质是把多次迭代的代码平铺为直线代码，1 次迭代无法平铺。

  只有 C > 4096（如 C = 8192 时每线程 2 次迭代）才存在可展开的空间，
  但即便如此，仍受下述原因二的限制。

3.2 原因二（用户指出，正确）：循环携带依赖阻止指令级并行
──────────────────────────────────────────────────────────

#pragma unroll 的收益来源于让多个独立迭代同时在流水线中执行（ILP）。
前提条件：相邻迭代之间没有数据依赖。

Kernel 2 内层循环——存在循环携带依赖（loop-carried dependency）：
  sumX += v.x + v.y + v.z + v.w;
  // 迭代 k+1 的 sumX 必须等待迭代 k 的加法完成后才能开始
  // 依赖链：sumX_k → sumX_{k+1} → sumX_{k+2} → ...

Kernel 4 Welford 循环——依赖链更严重：
  rowMean = rowMeanOld + meanDiff * 4 / count;   // 依赖上一迭代的 rowMeanOld
  rowVar  = rowVarOld  + ...;                    // 依赖上一迭代的 rowVarOld
  rowMeanOld = rowMean;   // 将结果传入下一迭代
  rowVarOld  = rowVar;

  迭代 k+1 的计算无法在迭代 k 完成前启动，不存在可并行的独立迭代。

对比：能从 unroll 获益的循环示例（SAXPY）：
  out[i]   = a * in[i]   + b;   // 迭代 0
  out[i+1] = a * in[i+1] + b;   // 迭代 1，与迭代 0 完全独立
  out[i+2] = a * in[i+2] + b;   // 迭代 2，与前两次完全独立
  // 三次迭代可以同时在 GPU 流水线中执行

展开 sumX 累加的效果：
  // 展开后看起来是：
  sumX += v0.x + v0.y + v0.z + v0.w;   // iter k
  sumX += v1.x + v1.y + v1.z + v1.w;   // iter k+1，仍然等待 iter k
  sumX += v2.x + v2.y + v2.z + v2.w;   // iter k+2，仍然等待 iter k+1
  // 执行时依然串行，没有获得 ILP

  若想真正利用 ILP，需要分拆累加器：
  sum0 += v0.x + v0.y + v0.z + v0.w;   // 独立
  sum1 += v1.x + v1.y + v1.z + v1.w;   // 独立
  sum2 += v2.x + v2.y + v2.z + v2.w;   // 独立
  sumX = sum0 + sum1 + sum2;            // 最后合并
  // 但 #pragma unroll 本身不会自动做这种变换

3.3 两个原因的适用范围
───────────────────────
  ┌──────────────────────────┬───────────────┬───────────────┐
  │ 场景                     │ 原因一是否生效 │ 原因二是否生效 │
  ├──────────────────────────┼───────────────┼───────────────┤
  │ C ≤ 4096（当前测试范围） │ ✓ 迭代≤1，    │ 不需要考虑    │
  │                          │   直接失效    │               │
  ├──────────────────────────┼───────────────┼───────────────┤
  │ C > 4096（假设扩展）     │ 有多次迭代，  │ ✓ 依赖链阻止  │
  │                          │   原因一失效  │   ILP，依然   │
  │                          │               │   无法获益    │
  └──────────────────────────┴───────────────┴───────────────┘

  两个原因叠加，使得 #pragma unroll 在当前 kernel 设计下
  对所有测试尺寸均无实质性收益。

--------------------------------------------------------------------------------
四、结论
--------------------------------------------------------------------------------

1. 当前测试范围（C ≤ 4096）内，每线程最多执行 1 次循环迭代，
   #pragma unroll 展开空间为零，是性能无提升的直接原因。

2. 即使扩展到更大的 C，循环携带依赖（sumX 累加链 / Welford 的
   rowMeanOld–rowVarOld 传递链）也会阻止 ILP，unroll 仍无效。

3. 想从 unroll 获益，需要将单个累加器拆分为多个独立累加器后合并，
   或改用迭代间完全无依赖的算法结构（如 SAXPY）。
