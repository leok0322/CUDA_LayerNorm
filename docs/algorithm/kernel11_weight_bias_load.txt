================================================================================
  Kernel 11：weight / bias 全 block 协作加载
  ── 相对 kernel 6 的改进
================================================================================

--------------------------------------------------------------------------------
一、kernel 6 的演变与现状
--------------------------------------------------------------------------------

  【原始版本】weight / bias 加载在 if 外，所有线程均执行：

    for (col = threadIDX; col < totalCol/4; col += threadNum) {
        scalar_t4 vecA      = ...A[row * totalCol + col * 4]...;
        scalar_t4 vecWeight = ...weight[col * 4]...;   // ← 所有线程加载
        scalar_t4 vecBias   = ...bias[col * 4]...;     // ← 所有线程加载

        rowMean += vecA.x + vecA.y + vecA.z + vecA.w;

        if (threadIdx.y == 0) {    // ← 只有第 0 行写 SMEM
            smemWeight[col][0..3] = vecWeight.x/y/z/w;
            smemBias  [col][0..3] = vecBias.x/y/z/w;
        }
    }

    问题：threadIdx.y=1 的线程加载了 weight/bias 但结果被丢弃，
          冗余 load 浪费指令和寄存器。

  【修改后（当前版本）】weight / bias 加载移入 if 内：

    for (col = threadIDX; col < totalCol/4; col += threadNum) {
        scalar_t4 vecA = ...A[row * totalCol + col * 4]...;
        rowMean += vecA.x + vecA.y + vecA.z + vecA.w;
        smemA[...] = vecA;

        if (threadIdx.y == 0) {    // ← load 和 store 均在 if 内
            scalar_t4 vecWeight = ...weight[col * 4]...;
            scalar_t4 vecBias   = ...bias[col * 4]...;
            smemWeight[col][0..3] = vecWeight.x/y/z/w;
            smemBias  [col][0..3] = vecBias.x/y/z/w;
        }
    }

    冗余加载问题已消除，但仍只有 BSX = 256 条线程负责加载 weight/bias，
    另外 256 条（threadIdx.y=1）不参与，内存请求密度仍为潜在上限的 50%。

--------------------------------------------------------------------------------
二、kernel 11 的改进：全 block 协作加载，独立循环
--------------------------------------------------------------------------------

  2.1 新增平铺线程索引
  ─────────────────────
    // 将二维线程号展开为一维，覆盖 block 内所有线程
    scalar_i threadIdxForLoadWeightAndBias { threadIdx.y * blockDim.x + threadIdx.x };
    scalar_i threadNumForLoadWeightAndBias { blockDim.y  * blockDim.x };

    BSX=256, BSY=2：threadNumForLoadWeightAndBias = 512
    线程 0..255（threadIdx.y=0）和线程 256..511（threadIdx.y=1）全部参与加载。

  2.2 独立的 weight / bias 加载循环（在 A 加载循环之前）
  ─────────────────────────────────────────────────────
    for (col = threadIdxForLoadWeightAndBias; col < totalCol/4;
         col += threadNumForLoadWeightAndBias) {
        scalar_t4 vecWeight = ...weight[col * 4]...;
        scalar_t4 vecBias   = ...bias[col * 4]...;
        smemWeight[col][0..3] = vecWeight.x/y/z/w;
        smemBias  [col][0..3] = vecBias.x/y/z/w;
    }

    随后的 A 加载循环去掉了 if (threadIdx.y == 0) 分支：
    for (col = threadIDX; col < totalCol/4; col += threadNum) {
        scalar_t4 vecA = ...A[row * totalCol + col * 4]...;
        rowMean += vecA.x + vecA.y + vecA.z + vecA.w;
        smemA[threadIdx.y * totalCol/4 * 5 + col * 5 + 0..3] = vecA.x/y/z/w;
        // ← 无 if (threadIdx.y == 0)，代码更简洁
    }

三、改进效果对比
--------------------------------------------------------------------------------

  ┌────────────────────────────────┬──────────────────────┬──────────────────────┐
  │                                │ kernel 6（修改后）   │ kernel 11            │
  ├────────────────────────────────┼──────────────────────┼──────────────────────┤
  │ weight/bias 加载线程数          │ BSX = 256            │ BSX × BSY = 512      │
  │ weight/bias 加载循环位置        │ A 加载循环内（if 内） │ 独立循环（if 外）    │
  │ 冗余 weight/bias load          │ 无（已移入 if 消除）  │ 无                   │
  │ if (threadIdx.y == 0) 分支     │ 有（每轮判断）        │ 无                   │
  │ A 加载循环的分支                │ 有（weight/bias 分支）│ 无                   │
  │ 每线程循环迭代数（cols=4096）   │ 4 次                 │ 2 + 4 = 6 次         │
  └────────────────────────────────┴──────────────────────┴──────────────────────┘

  并发内存请求密度（weight/bias 加载阶段）：
    kernel 6 ：256 条线程（8 warp）并发发出 ld.global
    kernel 11：512 条线程（16 warp）并发发出 ld.global，L2 带宽利用率和延迟隐藏更强

--------------------------------------------------------------------------------
四、同步位置说明
--------------------------------------------------------------------------------

  weight/bias 的独立加载循环仍在 if (row < totalRow) 内部：

    if (row < totalRow) {
        for (col = threadIdxForLoadWeightAndBias; ...) {
            smemWeight / smemBias 写入
        }

        for (col = threadIDX; ...) {    // A 加载，rowMean 累加，smemA 写入
            ...
        }
        // 一级 warp 规约，写 reduction[]
    }

    __syncthreads();    // ← sync 1，保护 smemWeight/smemBias/smemA/reduction
                        //   在 if 外，越界行线程也能到达，不会死锁

  weight/bias 和 smemA 共享同一个 __syncthreads()，
  因为它们都在 phase1 内完成，phase2 开始前统一同步一次即可。

--------------------------------------------------------------------------------
五、kernel 11 vs kernel 9：相同优化点下的性能差异
--------------------------------------------------------------------------------

  kernel 9 与 kernel 11 共享相同的两个关键优化：
    ① weight/bias 全 block 协作加载到 SMEM（flat 线程索引，全部线程参与）
    ② 输入行 A 缓存到 SMEM（s_in / smemA），方差阶段直接从 SMEM 复用

  但两者并不完全一致，核心差异如下：

  ┌──────────────────────────┬─────────────────────────┬─────────────────────────┐
  │                          │ kernel 9                │ kernel 11               │
  ├──────────────────────────┼─────────────────────────┼─────────────────────────┤
  │ BSX（每行线程数）         │ 32（1 warp / 行）        │ 256（8 warp / 行）       │
  │ 规约方式                 │ 单 warp reduce（5 shfl） │ 二级 warp reduce        │
  │ A 加载 cache hint        │ load128cs（.cs 流式）    │ 无 hint                 │
  │ weight/bias cache hint   │ load128（.ca 缓存）      │ 无 hint                 │
  │ SMEM bank conflict 处理  │ x128 结构体，无需 stride │ stride-5 布局           │
  └──────────────────────────┴─────────────────────────┴─────────────────────────┘

  性能差异的根本原因：BSX 与 totalCol 的匹配度
  ─────────────────────────────────────────────
  kernel 11 的 A 加载循环以 BSX=256 为步长：
    for col = threadIDX; col < totalCol/4; col += 256

  当 totalCol 较小时，threadIDX ≥ totalCol/4 的线程整个循环体一次不执行：

    totalCol = 128  → totalCol/4 =  32 → 仅  32/256 = 12.5% 线程参与 A 加载
    totalCol = 256  → totalCol/4 =  64 → 仅  64/256 = 25%   线程参与 A 加载
    totalCol = 512  → totalCol/4 = 128 → 仅 128/256 = 50%   线程参与 A 加载
    totalCol = 1024+→ totalCol/4 ≥ 256 → 100% 线程参与 A 加载

  kernel 9 的 A 加载以 WARP_SIZE=32 为步长：
    for c = threadIdx.x * 4; c < totalCol; c += 128

  BSX=32，totalCol ≥ 128 时所有 32 条线程始终全部参与，利用率恒为 100%。

  实测数据验证（GFLOPS，sm_86）：

  ┌──────────────┬──────────┬──────────┬──────────────────────────────────────┐
  │ (rows, cols) │ kernel 9 │ kernel 11│ 说明                                 │
  ├──────────────┼──────────┼──────────┼──────────────────────────────────────┤
  │  256 ×  256  │   76.7   │   46.3   │ K9 +66%（K11 仅 25% 线程参与 A 加载）│
  │  512 ×  512  │  158.0   │  160.1   │ 基本持平（K11 50% 线程参与）          │
  │ 4096 ×  128  │  241.0   │   85.5   │ K9 +182%（K11 仅 12.5% 线程参与！）  │
  │ 4096 × 4096  │  231.2   │  242.5   │ K11 +5%（双方 100% 参与，256 线程    │
  │              │          │          │ 并发带宽更高）                        │
  └──────────────┴──────────┴──────────┴──────────────────────────────────────┘

  规律：cols 越小 K9 优势越大（BSX=32 与小 cols 匹配）；
        cols ≥ 1024 后 K11 因 256 线程并发优势逐渐反超。

================================================================================
  Kernel 11 vs Kernel 6（修改后）：weight / bias 全 block 协作加载的性能影响
================================================================================

--------------------------------------------------------------------------------
一、实现差异（基于修改后的 kernel 6）
--------------------------------------------------------------------------------

  kernel 6（修改后）：weight / bias 加载移入 if (threadIdx.y == 0) 内
    for col in threadIDX..totalCol/4 step BSX:
        vecA = load A[row, col]              // 所有线程
        rowMean += vecA; smemA[y][col] = vecA
        if threadIdx.y == 0:
            vecWeight = load weight[col]     // 只有 threadIdx.y=0 的线程加载（BSX 条）
            vecBias   = load bias[col]
            smemWeight[col] = vecWeight
            smemBias[col]   = vecBias

    weight/bias 由 BSX = 256 条线程加载（占 block 的 50%）
    无冗余加载；A / weight / bias 仍在同一循环内（access fusion 保留）

  kernel 11：weight / bias 独立循环，全部 BSX×BSY 线程协作加载
    for col in threadIdxFlat..totalCol/4 step BSX*BSY:
        smemWeight[col] = load weight[col]   // 全部 512 条线程，每列只加载一次
        smemBias[col]   = load bias[col]

    for col in threadIDX..totalCol/4 step BSX:
        vecA = load A[row, col]
        smemA[y][col] = vecA                 // A 加载单独循环，无 if 分支

    weight/bias 由 BSX×BSY = 512 条线程加载（占 block 的 100%）
    两个循环串行执行，A / weight / bias 访问不融合

  注意：当 totalCol/4 ≤ BSX×BSY = 512 时，kernel 11 中 threadIdxFlat ≥ totalCol/4
        的线程实际不发出加载（循环条件不成立），参与线程数退化到 totalCol/4 条。

四、结论与原因分析
--------------------------------------------------------------------------------

  结论：
    修改后 kernel 6 的性能格局发生了变化：
    · 小 rows（≤512）+ 中大 cols：kernel 11 普遍领先，最大差距达 +51%
    · 大 rows（≥2048）+ 大 cols：kernel 6 持平或略优（最大 +9%）
    · 1024×1024 及以上大方阵：kernel 6 略占优

    整体平均（10 个典型维度，sm_86）：
      kernel 6  = 166.0 GFLOPS
      kernel 11 = 168.2 GFLOPS
      差距       = +2.2 GFLOPS（+1.3%）
    两者整体性能无本质差距，kernel 11 的全 block 协作加载改进在平均意义下
    未带来显著收益，优势仅体现在特定维度（小 rows + 中大 cols）。

  原因 1：weight / bias 加载线程数差距（小矩阵时 K11 优势的主因）
    kernel 6（修改后）：weight/bias 由 if (threadIdx.y == 0) 保护，
                         只有 BSX = 256 条线程（8 warp）负责加载；
    kernel 11          ：全部 BSX × BSY = 512 条线程（16 warp）参与，
                         并发发出的 ld.global 数量是 kernel 6 的两倍。

    更多并发线程带来两个独立收益：

    收益 a：延迟隐藏（latency hiding）
      更多 in-flight 请求使 SM 调度器在等待某笔数据返回时有更多备用请求可执行，
      在 occupancy 低（block 数少、可切换 warp 少）时尤为关键。

    收益 b：内存读取吞吐（memory throughput）
      GPU 内存子系统（L2 cache / 内存控制器）能同时处理的请求数有上限。
      weight / bias 被所有 block 共享，通常命中 L2 cache，瓶颈是 L2 带宽。
      16 warp 并发发射请求比 8 warp 更充分地占满 L2 请求队列，
      相同数据量在更短时间内完成读取，而非仅靠延迟隐藏来弥补等待。

    当 rows 小（block 数少）时，两个收益都更显著，kernel 11 的优势更明显。

    当 totalCol/4 ≤ 512 时（如 cols=1024 时 totalCol/4=256），
    kernel 11 中 threadIdxFlat ≥ 256 的线程不实际加载，
    两者参与线程数相同，kernel 11 的这一优势消失。

  原因 2：独立循环带来额外循环开销（大矩阵时 K6 优势的主因）
    以 4096×4096（totalCol/4=1024）为例，每条线程的循环次数：
      kernel 6 ：1 个融合循环，1024 / 256 = 4 次迭代（A + weight + bias 一并处理）
      kernel 11：weight/bias 循环 1024 / 512 = 2 次 + A 循环 1024 / 256 = 4 次 = 共 6 次

    kernel 11 每条线程多执行 2 次迭代，每次迭代都有 loop counter 递增、
    边界检查、地址计算等指令开销。

    大矩阵（rows 大）时 SM occupancy 高，TLP 已将内存延迟充分隐藏，
    瓶颈从"等待数据"转移到指令发射吞吐。此时 kernel 11 多出的循环指令开销
    在总执行时间中占比上升，成为两者差距的主要来源。
    kernel 6 用更少的迭代完成相同的内存工作，指令效率更高。
